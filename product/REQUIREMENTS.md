# Requirements in development

These worked entries develop the [ten proposed framing claims](../claims/CLAIMS.tsv). They are not approved requirements. A **seed** is already-published framing; a **derived hypothesis** adds a behavior or test to investigate; **Not filled** means no evidence or ruling has been entered. Resolve original evidence through [Sources](../SOURCES.md).

## R-01 — Pause and return to a shared resource

| Field | Working entry |
|---|---|
| Status | Derived hypothesis; not validated or approved |
| Seeds | FIA-002, FIA-003, FIA-004 in the claim register |
| Outcome / problem | Explore how communal engagement can pause for discussion without losing the resource context. This problem formulation is derived, not an observed user-research finding. |
| Proposed behavior | Let a person pause the guided resource flow, discuss, and return to the relevant point. |
| Non-goals | Translation recording and checking remain outside the proposed initial scope (FIA-001). |
| Rationale | Develop the published pause/discuss/resume framing into a testable behavior. |
| Acceptance hypothesis | In a prototype exercise, the person can pause and resume the intended resource without searching for it again. Record the actual outcome; no success threshold is set yet. |
| Dependencies | Resource identity and timing information must be understood (FIA-009); availability is unassessed. |
| Open questions | What must persist across a pause? Who operates the device during a group session? |
| Validation / authority | Not filled: research, prototype evidence and product ruling. |

## R-02 — Prepare and manage offline resources

| Field | Working entry |
|---|---|
| Status | Derived hypothesis; not validated or approved |
| Seeds | FIA-005, FIA-006, FIA-009, FIA-010 |
| Outcome / problem | Explore resource preparation for phone use when a connection is unavailable. |
| Proposed behavior | Offer a deliberate selection of content to download, show whether it is available offline, and allow its removal. The availability indicator is a derived design hypothesis. |
| Non-goals | No storage quota, supported-device list or delivery implementation is specified. |
| Rationale | Make the published offline selection/removal proposal concrete enough to examine. |
| Acceptance hypothesis | With a selected resource prepared, an offline exercise can open it; after removal, the interface accurately represents its availability. This is a proposed test, not observed behavior. |
| Dependencies | Actual Aquifer content, linked media, timing metadata, permissions and transfer behavior remain to be assessed. |
| Open questions | What constitutes a complete usable resource? How should interrupted downloads and insufficient space be handled? |
| Validation / authority | Not filled: resource assessment, device exercise and product ruling. |
